# Mobile App Readiness

This note tracks how close the VTM Companion is to behaving like an installable
mobile web app, and what is intentionally **not** done yet so we can stay
focused on the next step instead of the final goal.

It is a living document; update it whenever a checkpoint changes the answer to
any of the items below.

## Installability

The app is installable today on:

- **Android (Chrome / Edge / Brave)** — open the deployed URL, tap the
  three-dot menu → "Add to Home Screen" or wait for the install prompt the
  browser surfaces after a few seconds of use. It launches in standalone mode
  (no browser chrome) because of `display: "standalone"`.
- **iOS Safari** — Share → "Add to Home Screen". It launches standalone
  because of the `apple-mobile-web-app-capable` meta.
- **Desktop Chrome / Edge** — the install affordance appears in the address
  bar once the manifest and a usable icon are detected.

### How to test locally

1. From the repo root: `pnpm --dir artifacts/vtm-companion run build`.
2. Serve the built output (any static server works): `pnpm --dir artifacts/vtm-companion run preview` then open the preview URL in Chrome.
3. Open **DevTools → Application → Manifest**. Confirm name, short name,
   theme color, background, start url, and icons all show without warnings.
4. **DevTools → Lighthouse → "Progressive Web App"** category — expect green
   for installability, with the explicit warning that there is no service
   worker (intentional, see below).
5. From the same tab, address bar → install icon, or three-dot menu →
   "Install VTM Companion". Confirm it opens in its own window.
6. On mobile, deploy a preview build and "Add to Home Screen" from Chrome
   (Android) or Safari (iOS).

## Required before Android / Play Store packaging

These are the assets and decisions that would block a Trusted Web Activity
(TWA) or a Capacitor wrapper, not the daily install flow above.

### Visual assets still needed

- **Designer review of `icon-192.png` / `icon-512.png` / `icon-maskable-512.png`.**
  The current icons (generated by `scripts/generate-pwa-icons.mjs`) render
  a generic gothic companion mark — a red-outlined dark book with a red
  spine and a red blood drop on its charcoal cover, set on a near-black
  rounded tile — composed purely from geometric primitives so it scales
  cleanly and has nothing copied from official sources. The design uses
  red as accent (border + spine + drop) so the book silhouette reads
  cleanly at favicon sizes. It clears the install warnings and reads at
  every size, but a designer should still produce a final polished
  version before any store submission. The maskable PNG already keeps
  every shape well inside the safe zone (centered, comfortable margins)
  so launcher masks (circle / squircle / rounded square) never crop the
  artwork.
- **Feature graphic / screenshots.** Adding a `screenshots` field to the
  manifest surfaces a richer install UI on Chrome and on Play Store. Target
  at least one portrait and one landscape PNG of a representative screen
  (e.g. the Character Sheet and the Tools dice roller). Not added in this
  checkpoint because they need real designed captures.
- **iOS splash images.** Only needed if we want a non-generic splash on iOS
  standalone launches. Current setup falls back to the system default, which
  is acceptable.

### Tooling decisions to make later

- **PWA install only.** Lowest effort: do nothing more. The current setup
  already supports "Add to Home Screen" on Android and iOS. Pros: zero new
  dependencies, no store review. Cons: not discoverable on Play Store.
- **Trusted Web Activity (TWA)** via Bubblewrap. Wraps the deployed PWA in
  an Android app shell that can be published to Play Store. Pros: thin
  wrapper, same codebase, single source of truth. Cons: requires the PNG
  icons + signed APK + manifest matching the deployed origin via Digital
  Asset Links.
- **Capacitor wrapper.** Brings the app into a true Android shell with
  access to native APIs (file system, share, etc.). Pros: most flexible.
  Cons: now we maintain a Capacitor project alongside the web app and pull
  in a build pipeline. Only do this if we genuinely need a native API the
  PWA can't reach.

We should pick one only when there's a concrete reason to ship outside the
web. Until then, the PWA install path is enough.

## Deferred (intentionally NOT done in this checkpoint)

- **Service worker / offline caching.** Adding one without a clear update
  strategy can leave users on a stale build for days. The right time to add
  one is when (a) we have a final icon set so install audits stop flagging
  warnings, and (b) we choose a caching strategy that matches our deploy
  cadence (network-first for HTML, cache-first for hashed assets).
- **Background sync / push notifications.** Not in scope and require a
  backend the app deliberately does not have.
- **Accounts / cloud sync.** Out of scope — data stays in localStorage.
- **Capacitor / Tauri / Electron wrappers.** Not yet.
- **App shortcuts, share target, file handlers.** Premature without a final
  icon set.

## What this checkpoint did not touch

- `localStorage` keys, schemas, or any persistence behavior.
- Backup file format / import/export flow.
- Routes, navigation, or any page content.
- The Railway / static-host deploy pipeline. The added `manifest.webmanifest`
  is a plain static file under `public/` — Vite copies it to the build
  output as-is and any static host already serves the correct
  `application/manifest+json` MIME for `.webmanifest` files; no server
  config change is required.
